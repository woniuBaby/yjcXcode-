# Product Requirements

## 目的

把“原始需求”整理成一套可以驱动实现与测试的文档，而不是直接开始编码。

默认目标链路：

```text
需求文档（可能来自需求方）
-> 产品文档
-> 设计图（不一定需要）
-> 程序设计文档
-> 测试用例文档
-> 编码
-> 审阅和自测
-> 测试
```

## 何时必须先用本 skill

遇到下面任一情况，先写文档，再编码：

- 新增能力或新插件
- 对外 API、回调、事件、兼容性有变更
- 涉及宿主接入、系统权限、第三方 SDK、扩展 Target
- 用户明确要求先写需求/设计/测试文档
- 需求较大，单靠口头描述不足以稳定实现

## 小修例外

如果只是下面这类小改，可以不写完整长文档：

- 单点 bugfix
- 文案 / 注释 / 拼写修正
- 用户已明确范围的极小补丁

但仍要至少写一个简短变更说明，包含：

- 目标
- 影响范围
- 验收点

## 执行顺序

### 1. 先识别输入

先判断当前拿到的是哪一种输入：

- 需求方原稿
- 聊天里的口头需求
- 旧文档修订
- 现有代码反推需求

如果需求不完整，先补齐：

- 目标用户 / 使用方
- 目标行为
- 成功标准
- 兼容范围
- 约束与依赖

### 2. 产出产品文档

先写产品文档，再考虑实现。

默认内容：

- 背景
- 目标
- 非目标
- 角色 / 使用方
- 用户流程或调用流程
- 功能需求
- 边界条件
- 错误与降级
- 兼容性
- 验收标准
- 风险与待确认项

若仓库已有固定目录，优先沿用；在 NativeBility 中默认落点为：

- `NativeBility/docs/requirements/<topic>.md`

### 3. 判断是否需要设计图

不是每个需求都要画图。只有在下面情况才建议补设计图或结构图：

- 涉及多个系统/Target/Extension/第三方 SDK 的交互
- 事件流或时序复杂
- 多端桥接链路复杂
- 单靠文字难以说清

如果不需要设计图，在文档里明确写“本需求无需单独设计图，文字与流程图足够”。

### 4. 产出程序设计文档

程序设计文档关注“怎么实现”，而不是“为什么做”。

至少写清：

- 改动文件 / 模块
- 类与职责拆分
- 数据结构 / 输入输出模型
- API / 回调 / 事件
- 第三方依赖与开关
- 线程 / 缓存 / 持久化 / 通知
- 降级与错误处理
- 与现有实现或旧版本的兼容策略

### 5. 先写测试用例文档

测试用例文档必须在编码前定义边界。

至少覆盖：

- 正向路径
- 失败路径
- 降级路径
- 边界输入
- 回调 / 返回格式
- 宿主集成前提
- 回归判定标准

目标是让后续编码不会“写完才想边界”。

### 6. 再进入编码

只有在产品文档、程序设计文档、测试用例文档足够支撑实现时，才开始编码。

编码时始终回看文档：

- 若实现与文档一致，继续
- 若实现发现文档有误，先修正文档或明确说明偏差

### 7. 审阅和自测

编码后，至少做：

- 代码审阅
- 自测
- 与测试用例文档逐项核对

不要只说“代码写完了”，要明确：

- 哪些用例已验证
- 哪些没法在当前环境验证

## 默认输出清单

除非用户另有要求，尽量形成这三类文档：

1. 产品文档
2. 程序设计文档
3. 测试用例文档

如果任务规模很小，可压缩成：

1. 简版产品说明
2. 简版设计说明
3. 简版验收/测试点

## 文档写作要求

- 文档必须可执行，不写空泛套话
- 验收标准必须可测试
- 边界条件必须提前写出
- 兼容性、依赖、宿主前提必须显式写
- 对外行为变化必须明确迁移影响
- 如果后续希望“删代码后还能重建”，实现文档必须写到字段、回调、事件、降级细节级别

## 与规则联动

如果项目规则提到“先用 `product-requirements` 再编码”，执行时按本 skill 落地，不跳过文档阶段。
